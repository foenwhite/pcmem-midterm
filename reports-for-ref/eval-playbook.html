PC-Mem 评测运行手册：按硬件条件选模型与估时

知识图谱课程项目 pj01 · 选题 1「全 PC 文件管理记忆系统」· v1.8 候选实现（schema 0013）

适用读者：拿到本仓库、要在自己机器上产出可用于报告的数字的同学。本文不假设你已有任何密钥，也不假设你在这台机器上跑过。

v2 · 2026-11-10。本版改了三处结论：建图改成并发之后，只有 API 也能给公开 benchmark 建全量图（1 小时、约 ¥5，代价是约 15 行代码补丁，见第 2、4 节）；数据集按「语料能不能建图」重估，而不是按「转换器好不好写」（第 6.3 节）；kg 条件其实是三层叠加，kg − rag 不能算作图的作用（第 1、7 节）。

一句话结论。三种处境各有一个最划算的数据集与一套固定的模型组合：有 GPU 就冲 MultiHop-RAG 全量三条件（端到端约 2 小时）；只有 API 就跑 MultiHop-RAG 1/4 分层抽样 639 题、但现在可以把图一起建（约 3 小时，约 ¥8）；只有 Mac 就把个人语料控制在 300 个 chunk 以内，或者把建图挪到 API（8 分钟、约 ¥0.6）。公开 benchmark 只回答「图与纯检索差多少」，版本链、项目归属、时间线、增量刷新、异构解析这五项它一个都测不了，必须靠自己的语料另开一组。

先记住四件事。模型分四个角色，各有各的上限，选错一个就白跑：向量化锁死本地 Qwen3-Embedding-0.6B / 1024 维；判分模型必须和答题模型不同家族（默认继承答题模型，等于自己给自己打分）；抽取与判分只选非思考模型（输出上限 8192 / 1024 token 会被 thinking 吃光）；一个 SCI_RAG_OPENAI_BASE_URL 只能指一个端点，所以「本地答题 + 别家判分」要靠原生 provider 绕。

1. 先看清评测面：两个命令加一条 benchmark runner

仓库里有三个不同的东西都叫评测，别混。它们吃不同的模型，也回答不同的问题。

入口回答什么问题消耗什么能否离线
sci-rag eval retrieval --ablation每一层检索（向量、关键词、图、社区、HyDE、重排）各自贡献多少embedding 加 HyDE 的少量生成基本可以，只要 embedding 在本地
sci-rag eval answers答案有没有被来源支撑，引用对不对，和参考答案一致吗每题 1 次答题加 2 次判分不行，必须有生成凭据
scripts/run_benchmark_eval.py同一批题上 plain（无检索）、rag（向量加关键词）、kg（全层）三条件对比每题 × 3 条件 ×（答题加 2 次判分）不行

三个条件天然共用一切资产，所以只需要跑一遍。plain（无检索）、rag（向量加关键词）、kg（全层）共用同一份语料、同一套向量、同一个答题模型、同一批题目，只差三个 layer 开关（run_benchmark_eval.py:69 的 RAG_LAYERS），所以它们是配对设计：一次 ingest 摊三份，McNemar 直接给出 p 值，样本量不用翻倍。但 kg 打开的是图、社区、HyDE 三层，因此 runner 里 kg − rag 的差额不是「图的贡献」，要拆开只能靠本节表格里那个 eval retrieval --ablation 的 no_graph 行。两条一起报：runner 给端到端，ablation 给归因。

关键分工。公开 benchmark 测不了本项目的立论：版本链、项目归属、时间线浏览、增量刷新、异构解析这五项必须靠自己的语料。所以报告里本来就要两组实验：公开 benchmark 回答「图与纯检索的差别」，个人语料回答「结构化到底补了什么」。选数据集时按这个分工选，别指望一个数据集全包。

写入代码的四个输出上限

这些是硬编码的，选模型前先对照。带 thinking 的模型一律不要用在抽取和判分上。

调用点输出上限行为
图抽取 graph/extractor.py:414819210 个 chunk 一批实测要吐约 6,200 token；顶上就截断 JSON，批内拆分重试，单次调用几十秒
实体消解 graph/resolve.py:1744096只在 graph resolve-entities 时用
答题 answer/generator.py:1242048够用；--limit 8 个来源时容易顶满
判分两趟 evals/judge.py:77,1011024 / 512要的是短 JSON，思考 token 会把它吃干净，判分全部校验失败
HyDE / 图实体 / 社区摘要512 / 512 / 400短调用，便宜

向量化别乱换。Qwen3-Embedding-0.6B 原生 1024 维，正好落在 pgvector HNSW 的 2000 维上限内。4B / 8B 版本原生是 2560 / 4096 维，而代码里的维度校验只检查不截断（embed/provider.py:53 的 assert_dimension），换上去直接抛 EmbeddingDimensionError；就算手动截断，也要全量重灌。结论：这个角色不参与选型，一律用 0.6B 加 1024 维。

不是上限，但比上限更硬：抽取在代码里是串行的

这一条决定了「用 API 能不能给公开 benchmark 建图」。extract_graph 是一个逐批 await 的 for 循环（graph/extractor.py:305-317），没有任何 gather；build_communities 同样是逐簇串行（communities.py:130-140）。所以「调 API 加并发」本身不成立，必须先改代码：把那个循环换成 asyncio.gather 加 semaphore，约 15 行，建议做成默认 1 的 --concurrency 参数，不改变现有行为。

改起来是安全的：每批写库自己开 session，写段被 pg_advisory_xact_lock 保护（versions.py），并发时只有落库那几十毫秒串行，LLM 调用是真并行。别用「多开几个进程」这个偷懒办法：pending 在进程启动时选一次（extractor.py:281-295），N 个进程会挑到同一批 chunk，N 倍重复烧钱、零加速。

MultiHop-RAG 全量建图（约 2,400 chunk、240 次调用）时间说明
现状：串行13.3 h240 次 × 200 s（实测 9 次 / 30 min）
改后：并发 8约 60 min受单流解码限制（每流 40–60 token/s），此时还没撞配额
改后：并发 12–16约 45 min再往上只是在 429 上排队，不再变快

抽取可续跑：处理过的 chunk 记在 chunk.graph_extracted_at 上，中断之后重跑只做剩下的（extractor.py:287）。所以「一次 429 连击就整段作废」这个顾虑不成立，最坏情况只是慢。

一个容易踩的坑：只有一个 OpenAI 兼容 base URL

配置里只有一个 SCI_RAG_OPENAI_BASE_URL。所以你不能「答题指向本地 vLLM、判分指向另一台机器」，除非判分走原生 provider（deepseek:、anthropic:、google:）。同一家 API 上有多个家族的模型时（比如同时提供 Qwen 和 DeepSeek），就完全没问题，换 model id 即可。

答题在哪判分怎么做到不同家族写法
本地 vLLM / llama.cpp只能走原生 providerSCI_RAG_JUDGE_MODEL=deepseek:deepseek-v4-flash
同一家聚合 API换一个家族的 model idopenai-compatible:deepseek-ai/DeepSeek-V4.1-Flash

3. 方案 A：有 GPU（A100 80G / 4090 24G / 任意 CUDA 机器）

数据集：MultiHop-RAG 全量。理由：GPU 消掉了 API 的每分钟 token 上限，而这份语料只有 609 篇，建图能在半小时内做完。v2 之前这是唯一能「跑全量又带图条件」的组合；现在只有 API 也能做到（第 4 节），GPU 的优势退成两条：不用改代码，也不占配额。

上一版的结论被推翻了。「不要在 API 上给公开 benchmark 建全量图」那个判断，依据是串行的十几个小时（约 240 次调用 × 200 s）。打完并发补丁之后，MultiHop-RAG 的图是 1 小时、5 块钱，可以建，不必再把图这一半推给 GPU 或小语料。真正建不起图的是段落级大语料：HotpotQA / 2Wiki / MuSiQue 那类 1.5 秒一个 chunk 乘以 3–7 万个 chunk，谁也救不回来。

还有一条容易忽略的：TPM 与 RPM 是账号级、按模型独立计的（硅基官方限流文档）。所以当建图和答题用的是同一个 30B-A3B 时，两者会互抢同一个 TPM 池：建图占去约 3.7 万/分，答题只剩 1.3 万，反而比单独跑更慢。先建图、再问答；真要并行，就把其中一件挪到另一个账号或另一个模型上。

并发：先算上限，再决定 --concurrency

最重要的一条。重试策略是硬编码的 3 次尝试、1s 到 2s 退避（llm/client.py:31,66-86，429、408、5xx 会重试，但总共只多等 3 秒）。一旦你把并发开到超出配额，任务不是变慢，而是在第 3 次尝试后直接抛异常中断。并发数必须按配额算，不能试出来。

一次 question-run 的成本是固定的：约 1,545 输入 token 加约 600 输出 token，合约 2,100 token（答题一次加判分两趟）。于是：

安全并发 ≈ (每分钟 token 配额 ÷ 2,100) × 单次耗时(秒) ÷ 60

# 实测口径：配额 50,000 token/min -> 约 23 run/min；单次约 20 s
(50000 / 2100) × 20 / 60 ≈ 7.9   ->  --concurrency 8    （仓库实测值）
# 若配额是 250,000 token/min -> 约 119 run/min
(250000 / 2100) × 20 / 60 ≈ 39.7 ->  --concurrency 32–40
你的配额吞吐上限建议 --concurrency观察点
50k token/min（低档）约 23 run/min8日志出现 llm_retry 就说明已经压满了
150k token/min约 71 run/min16–24同上
250k token/min 以上约 119 run/min32–40再高只是把 429 堆起来

其它与并发相关的实操点：

  • eval answers 的 --concurrency 默认是 1，不显式设就是串行，会把 1.9k 次跑成十小时。远程 API 一定要设。
  • eval answers 的 --limit 是每次答题取几个来源（默认 8），不是题量。要缩题量就把问题写成单独的 JSONL 用 --questions 指过去。
  • 建图的并发必须先改代码（第 2 节那个 15 行补丁），改完之后的上限由 TPM 和单流解码速度共同决定：单流 40–60 token/s，8 路并行约 3.9 次调用/分；到 12 路以上就只剩 429。
  • 先跑 eval retrieval --ablation：它只吃 embedding 和 HyDE（512 token 一次），几乎不花配额，却能先确认语料和问题集是好的。

表里「50k/min 下」一列按仓库实测口径：答题与两次判分都打在同一家。把判分挪到另一家之后，硅基这边只剩答题那一次调用（约 1,200 token），50k 配额对应约 40 run/min，所以实际用时约为表内数字的六成。

要在 API 上建全量图，两个前提。第一，先给 extract_graph 打并发补丁，否则 609 篇是 13 小时而不是 1 小时（见第 2 节）。第二，接受它会把 TPM 池子占满，所以建图期间不要同时跑问答；顺序上先建图、再问答。其余担心可以放下：抽取是可续跑的，429 只会让它变慢，不会让前面的工作作废。

5. 方案 C：只有 Mac / 笔记本

数据集：自己的个人语料，5–20 篇、100–300 个 chunk。理由：笔记本上建图约 20 秒一个 chunk（7B Q4，40 token/s 解码），公开 benchmark 的 609 篇在笔记本上要十几个小时，性价比为负；而个人语料恰好是公开 benchmark 测不了的那五项（版本链、项目归属、时间线、增量刷新、异构解析）唯一的证据来源。

想要一个公开数字垫底，就在 MultiHop-RAG 上取 40–60 篇子集做冒烟，并明确写它是冒烟而不是结论。或者更省事的做法：本地只做摄取与嵌入，把建图也挪给 API（打完第 2 节那个补丁后，300 chunk 只要约 8 分钟、约 ¥0.6），这台笔记本就真的只承担它擅长的事。

7. 通用纪律与验收清单

  1. 向量化不参与选型。一律 Qwen3-Embedding-0.6B / 1024 维，灌库前定好；改它等于迁移加全量重嵌。
  2. 判分必须换族。不设 SCI_RAG_JUDGE_MODEL 就等于自己给自己打分。仓库里已提交的那次 4 题冒烟就是同模型自评，只能当冒烟看。
  3. 一次只动一个变量。换模型不是「检索改进」，eval diff 会把它当成改进报出来，报告里要分开写。
  4. 「图有没有用」要两条证据。runner 的 kg − rag 里混着图、社区、HyDE 三层，只能当端到端看；逐层归因靠 eval retrieval --ablation 的 no_graph 一行。两个一起报，否则一句「你凭什么说这是图带来的」就答不上来。
  5. 配额按模型算、按账号算。建图与答题同用一个模型时共享同一个 TPM 池，先建图再问答；判分换到另一家不只是为了「不自己给自己打分」，也是把两次调用挪出配额池、直接换吞吐的手段。
  6. 每份报告必须能自证。语料快照、git commit、答题／抽取／判分三个模型 id、启用的层，一个不能缺；问题里只要还有 drafted 标签，数字就是暂定的。
  7. 判分先用 30 条人工标签校准。sci-rag eval calibrate --labels labels.jsonl --report .../report.json，低于 30 条 kappa 不稳，这一列只能当参考。
  8. 留一条反幻觉探针。问题集里至少一条 unanswerable；它答得斩钉截铁就先修答案 prompt，别调检索。
  9. 产物都放 PCMEM_DATA_DIR 下。跑完归档证据、停掉自己起的服务、清掉临时库，只留源码、回归夹具、报告与复现元数据。
