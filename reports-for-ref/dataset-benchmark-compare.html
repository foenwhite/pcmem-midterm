06 反面样本：MultiHop-RAG 没有文件树

现有 eval 的主力 corpus.json 是一个扁平的文章数组，每条只有 7 个字段。没有 path / folder / dir / version，每题的 evidence_list 用 title / url / fact 指向 2–4 篇独立新闻文章（论文口径 609 篇 / 2,556 题）。

// corpus.json 的单条结构
{ "title": …, "author": …, "source": …, "published_at": …,
  "category": …, "url": …, "body": … }

所以它本质是 article-level multi-hop retrieval：语料是「一堆文章」，不是「一台电脑」。它能覆盖的只有 A8（图 vs 纯检索、null 题拒答）与 A1 的文本部分（但只有 news 一种体裁）；A2 版本、A3 项目、A4 引用、A5 时间线、A6 增量全部 ❌。

正文里偶尔出现的 “UPDATE:” 是新闻编辑痕迹，不是版本标注，不能当版本链用。

Track 2 · 自建 personal corpus（回答「结构化到底补了什么」）

基底二选一

xAFS（推荐）：CC-BY-4.0，837 MB，dp_007(200) + dp_008(299) + dp_009(480) ≈ 979 文件，天然有项目命名与跨上下文文件；适合注入版本链。

HippoCamp subset：158+147+137 = 442 文件，真实文件 + 多模态；但 research-only，且向真实 docx/pdf 注入合成版本很别扭 —— 更适合作为不改动的外部多模态验证集。

在基座上受控注入（核心贡献）
  1. 版本链：60–100 条，每条 3–5 版；命名模拟 _v1 / _final / _final(2) / 副本；每版替换 1–3 个关键事实，保留「旧版仍可检索」
  2. 项目归属：3–5 个项目，文件跨 4–6 个目录；15–20% 同主题错项目 distractor
  3. 引用边：wikilink / DOI / 文件名 mention，带可验证 quote
  4. 时间线：mtime + 内容内日期；制造 1–2 处冲突
  5. 增量序列：3–5 个摄入 wave，含 supersede / rename / delete / restore
  6. 抽取 gold：40 个文件标注实体+关系（或由生成器同时产出 planted facts）
  7. QA：150–250 题，覆盖 8 类

规模控制：目标 400–800 文件 / 3–5k chunks。这与仓库自己给出的「Mac 上不超过 300 chunk」建议冲突 —— 若坚持本地 7B，把注入语料压到 300 chunk，大基座留给 Track 1；若走 API/GPU，再放大到 3–5k。

Track 3 · 可选：Agent 行为

Personal Agent Bench 的 12 任务 demo（尤其 tax_packet 三个 seed）可直接复用其 oracle 做「版本选择 + decoy 判别」的行为指标；但需要接它的 harness，成本高于 Track 1/2，建议只在 demo 里展示、不进主实验。
